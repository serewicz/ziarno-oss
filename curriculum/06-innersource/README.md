# Module 6: InnerSource: open-source practices inside first

**Level:** Practitioner  
**Time:** about 4 hours  
**Needs:** a laptop or a phone with a browser; some exercises need an internet connection once.

## Learning objectives
By the end you will be able to:
- Explain InnerSource: using open-source ways of working inside one ministry or company
- Describe the Trusted Committer and InnerSource Champion roles
- Explain how InnerSource and the OSPO work together
- Start one InnerSource project with a README, CONTRIBUTING file, and a named Trusted Committer

## Lesson outline
1. What InnerSource is: shared code, open review, and written decisions, but only inside the organization
2. Why start here: teams can practice in a safe space before they work in public
3. Trusted Committers: people who review and accept contributions and mentor newcomers
4. InnerSource Champions: people who promote the practice and help teams adopt it
5. How it fits the OSPO: the OSPO sets policy and moves good InnerSource projects to public release
6. Patterns from InnerSource Commons: a README for guests, 30-day warranty, Trusted Committer
7. From InnerSource to open source: checklist before going public (license, secrets removed, security review)

## Hands-on exercise: Turn one internal tool into an InnerSource project
1. Pick a small internal tool or script that more than one team uses.
2. Put it in your internal git server (GitLab, Gitea, or similar) if it is not there already.
3. Open https://patterns.innersourcecommons.org/ and read the patterns **Standard Base Documentation** and **Trusted Committer**.
4. Write a README.md: what the tool does, who owns it, how to run it, how to ask for help.
5. Write a CONTRIBUTING.md: how to report a problem, how to propose a change, how long a review should take.
6. Name one Trusted Committer and write their name in CONTRIBUTING.md.
7. Tell one other team the project is open to them and invite one small change.
8. After a month, note: how many changes came from outside the owning team, and how fast they were reviewed. Share this with the OSPO.

## Quiz
1. What is a Trusted Committer?
2. Why practice InnerSource before working in public?
3. Who decides when an InnerSource project becomes public?

<details><summary>Answers</summary>

1. A person who reviews and accepts contributions, keeps quality, and mentors contributors.
2. Teams learn open ways of working where mistakes are private and the risk is low.
3. The OSPO, using the release policy.

</details>
